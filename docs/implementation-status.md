# 구현 현황

프론트엔드를 먼저 전부 만들고, 그 뒤에 백엔드(Express + MySQL)를 붙인다.
백엔드가 없는 동안 데이터는 MSW 가 공급한다.

**최종 갱신**: 2026-09-02 · 전체 점검 — 날짜 버그 수정 · **브라우저 검증을 저장소로 이관**

## Phase 2 — 타입 · API 계층 ✅

**타입** (`src/types/`) — 블루프린트 §3·§4·§8 을 옮겼다. `auth` · `roster` · `board` · `schedule` · `activity-log` 5개 파일.

API 응답 필드는 **camelCase 로 통일**하기로 정했다. 구 API 는 `staff_type`(snake)과 `isPinned`(camel)가 한 응답에 섞여 있었다 — MySQL 컬럼명이 그대로 새어나온 결과다. 새 백엔드가 변환해 내려준다.

타입을 쓰면서 구 스키마의 문제를 함께 정리했다.

| 구 문제 | 새 타입에서 |
|---|---|
| §12-24 `events.type` 주석(`anniversary`)과 실제 ENUM 불일치 | 실제 값(`training/meeting/events/etc`)만 타입에 존재. 잘못 쓰면 컴파일 에러 |
| §12-19 `membership_status` 가 신청 상태와 차단을 겸함 | `MembershipStatus` 에서 `banned` 를 빼고 `isBanned` 분리 |
| §12-20 `holidays` 는 year/month/day, `events` 는 DATE | `Holiday.date` 를 `'YYYY-MM-DD'` 로 통일 |
| §12-23 미사용 컬럼(`kakao_id`, `marketing_sms/kakao`) | 타입에서 제외 — 새 스키마에서 만들지 않는다 |

**권한** (`src/lib/roles.ts`) — **§12-18 결함을 고치는 파일이다.** 구 구현에는 역할 순위 비교 함수가 없어 열거가 코드 전반에 흩어져 있었다. `ROLE_ORDER` + `hasAtLeast` 를 두고 §4.4 매트릭스 전체를 함수로 표현했다.

§4.3 이 지적한 시그니처 불일치(프론트는 `user` 객체, 백엔드는 `role` 문자열)도 **role 문자열 하나로 통일**했다. 프레임워크 의존성이 없어 백엔드가 그대로 import 할 수 있다.

§8.4 의 로그 열람 규칙(`canViewLogsOf`)도 구현했다 — 구 구현은 이걸 프론트 탭 표시 조건으로만 두고 API 는 완전 공개였다(§12-2).

**API** (`src/lib/api.ts`, `src/lib/token.ts`, `src/hooks/useApiErrorHandler.ts`)

계획에서는 "status → 화면 이동 매핑을 `api.ts` 한 곳에 둔다"고 했으나 **정책과 실행을 분리하는 쪽으로 바꿨다.** `api.ts` 는 컴포넌트가 아니라 `useNavigate` 를 쓸 수 없고, navigate 함수를 전역 등록하면 테스트가 어려워진다.

- `api.ts` — `ApiError`(status 보존) · `NetworkError` 를 던지고, `errorRoute(status)` 순수 함수로 목적지만 정한다
- `useApiErrorHandler` — 실제 이동을 담당. **반환값이 계약이다**: `true` 면 처리 완료, `false` 면 화면을 옮기지 않았으니 호출부가 인라인으로 표시해야 한다(400·409 등, `docs/error-screens.md` 3절)
- 401 이면 만료된 토큰을 지우고 `returnTo` 를 붙여 `/401` 로 보낸다

## Phase 3 — MSW 목 서버 ✅

**공개 조회 8종** — `GET /api/posts/recent` · `/api/roster/years` · `/api/roster/active-year` · `/api/roster` · `/api/events` · `/api/holidays` · `/api/records/batting` · `/api/records/pitching`

**인증 7종** (§5.1) — `POST /login` · `/signup` · `/send-email-code` · `/verify-email-code`, `GET /me` · `/check-username` · `/check-email`

- `src/mocks/fixtures/users.ts` — 역할·상태별 계정 8개(basic 미신청 / basic 승인대기 / member / manager / staff 회장 / staff 감독 / root / 차단)
- `src/mocks/authState.ts` — 세션·사용자·이메일 인증 상태. 회원가입이 실제로 반영된다
- `src/mocks/authGuard.ts` — **판정에 `lib/roles.ts` 의 `hasAtLeast` 를 그대로 쓴다.** 프론트와 목이 같은 함수를 쓰면 어긋날 수 없다. 차단 계정도 여기서 거른다(§12-4)
- `src/mocks/devAuth.tsx` — 개발 전용 역할 전환기

> **§12-3 결함 수정.** 구 구현은 이메일 인증 성공 사실을 서버에 남기지 않아 API 를 직접 호출하면 임의 이메일로 가입할 수 있었다. 목은 인증된 주소 목록을 서버 쪽에 두고 `/signup` 에서 검사한다. **API 직접 호출로 우회가 막히는 것을 브라우저에서 확인했다**(400 "이메일 인증을 먼저 완료해 주세요").

**일정 쓰기 4종** — `POST /api/events` · `POST /api/events/bulk` · `PUT /api/events/:id` · `DELETE /api/events/:id`. 전부 **manager+** 이며 `authGuard.requireRole` 로 막는다. `UNIQUE(date, name)` 위반은 409.

`src/mocks/scheduleState.ts` — 일정의 변경 가능한 저장소. 픽스처는 호출마다 새로 생성되므로 추가·수정·삭제를 끝까지 걸어보려면 한 번 만들어 들고 있어야 한다.

> **목의 한계**: 쓰기 상태는 **탭 메모리에만** 산다. 새로고침하면 초기 픽스처로 돌아간다. 화면 흐름을 확인하기에는 충분하지만, 검증 스크립트는 이 성질을 알고 있어야 한다(중복 테스트를 방금 만든 일정이 아니라 픽스처에 원래 있는 일정으로 하는 이유다).

**게시판 12종** — 조회를 **권한별로 셋으로 나눴다**(§12-1).

| 엔드포인트 | 권한 |
|---|---|
| `GET /api/posts/recent` | 공개 — 홈 위젯용 축약(제목·날짜·유형만) |
| `GET /api/posts?page=&size=` | basic+ — 목록, 본문 없음 |
| `GET /api/posts/:id` · `/:id/adjacent` · `GET /api/comments` · `GET /api/polls/post/:postId` | member+ |
| `POST /api/posts` · `/api/comments` · `/api/polls/:id/vote` | member+ |
| `PUT /api/posts/:id` · `PUT /api/comments/:id` | **소유자만** |
| `DELETE /api/posts/:id` · `/api/comments/:id` | 소유자 또는 manager+ |

`src/mocks/boardState.ts` — 게시글·댓글·투표의 변경 가능한 저장소. 투표 자료구조가 이번 설계의 핵심이다.

```
polls / pollOptions(voteCount)
voters:       Set<`pollId:userId`>   ← 중복 방지·참여 여부만. 무엇을 골랐는지는 없다
namedChoices: Map<`pollId:userId`, optionIds[]>   ← 기명 투표에서만 기록
```

> **투표 생성·수정 엔드포인트는 없다.** 게시글 수정(`PUT /api/posts/:id`)에 딸려 서버가 UPSERT 하고, **옵션 텍스트가 그대로면 표를 보존한다**(§12-8). 구 구현은 클라이언트가 `DELETE 투표` → `PUT 글(INSERT)` 로 두 번 불러서, 옵션을 하나도 안 바꿔도 표가 전부 사라졌다.

> **익명 투표는 다시 던질 수 없다.** 서버가 누가 무엇을 골랐는지 저장하지 않으면 재투표 시 이전 표를 깎을 방법이 없다. 링크를 남기면 익명이 깨지므로 둘은 양립하지 않는다 — 실제 익명 투표 시스템이 한 번 던지면 확정인 것과 같은 이유다. 화면에도 그 사실을 적는다.

**마이페이지 13종** — 전부 로그인 필요, 활동 조회 4종은 member+.

| 엔드포인트 | 권한 | 비고 |
|---|---|---|
| `GET /api/mypage/me` · `check-username` · `check-email` | 로그인 | 중복 검사는 **본인을 제외**한다 |
| `PUT /api/mypage/account` | 로그인 | **이메일을 바꾸면 서버가 인증을 확인**(§12-3). 중복 409 |
| `PUT /api/mypage/password` | 로그인 | **신규.** 현재 비밀번호 불일치 400, §7.2 규칙 위반 400 |
| `PUT /api/mypage/profile` | 로그인 | `membershipStatus ∈ {none, rejected}` 일 때만. 아니면 403 |
| `POST /api/mypage/membership-request` | 로그인 | §7.1 전제조건 4가지 |
| `GET /api/mypage/roster-history` | member+ | **`userId` 기준** 조인(§12-17) |
| `GET /api/mypage/posts` · `comments` · `logs` | member+ | `{ items, page, size, total }` |
| `GET /api/mypage/votes` | member+ | 익명 투표는 `myChoices: null` |
| `DELETE /api/mypage/withdraw` | 로그인 | root 는 403. **익명화**(§12-12) |

`src/lib/membership.ts` — §7.1 의 전제조건과 전이를 프레임워크 없는 순수 함수로 뺐다. **화면의 버튼 활성화 조건과 서버 검사가 같은 함수를 쓴다** — 구 구현은 UI 가 학번을 "선택"으로 표기하고 서버는 없으면 400 을 반환해 서로 달랐다(§12-13).

**감사 로그** — `src/mocks/logState.ts`. §8.2 규약대로 **절대 throw 하지 않는다**(로그 실패가 사용자 동작을 막으면 안 된다).

지금까지 어떤 쓰기 핸들러도 로그를 남기지 않았다. 로그 탭만 만들면 픽스처만 보이고 방금 한 행동은 나타나지 않아 **화면이 거짓말을 하게 되므로**, 기존 핸들러(게시글 · 댓글 · 투표 · 일정)에 기록을 소급 적용했다. 각 핸들러에 `log(...)` 한 줄만 붙였고, **게시판 55항목과 일정 검증을 그대로 다시 돌려 기존 동작이 그대로임을 확인**했다.

> **수정 로그에 before/after 를 둘 다 남긴다(§12-7).** 구 구현은 수정 *후* 값만 남겨 무엇이 어떻게 바뀌었는지 알 수 없었다. 로그 상세에서 변경 전·후를 나란히 보여준다.

> **`vote_submit` 스냅샷에 선택 내용을 담지 않는다.** 담는 순간 §12-9 에서 어렵게 만든 익명성이 감사 로그를 통해 그대로 새어 나간다. 남기는 것은 "언제 어느 투표에 참여했는가"까지다. **로그 전체를 문자열로 뒤져 내가 고른 항목이 없음을 확인했다.**

**관리자 24종 · 활동내역 5종** — `handlers/admin.ts` · `handlers/users.ts`.

`src/mocks/rosterState.ts` — 로스터는 지금까지 정적 픽스처를 그대로 반환했다. 관리자가 편집하려면 변경 가능한 저장소가 필요하다. 활성 연도(`settings.active_roster_year`)도 여기 있다.

> **§12-2 — §12 에서 가장 심각한 항목.** 구 `GET /users/:username/logs` 는 인증이 **전혀 없었다.** "열람자 > 대상" 규칙은 프론트 탭 표시 조건일 뿐이라 `curl` 한 번이면 삭제된 게시글 본문과 실명·학번 스냅샷이 다 나왔다. 이제 서버가 `canViewLogsOfUser` 로 판정한다.

> **§12-10 — 승인이 조용히 실패하지 않는다.** 구 구현은 `WHERE authority='basic'` 에 기대면서 `affectedRows` 를 안 봐서, 이미 멤버인 사람을 승인하면 **아무것도 안 바뀌는데 "승인 완료"가 나가고 로그까지 남았다.** 먼저 확인하고 어긋나면 409 이며, **실패한 승인은 로그를 남기지 않는 것도 확인**했다.

> **§12-6 — 공휴일 자동 동기화를 없앴다.** 구 구현은 데이터 없는 연도를 **조회하기만 해도** 외부 API 를 호출하고 DB 를 갈아엎었다. 인증 없는 `?year=1900` 반복으로 쿼터를 태울 수 있었다. 이제 staff+ 가 설정 탭에서 눌러야만 돈다.

**`lib/roles.ts` 에 `canViewLogsOfUser` 추가** — 순수 역할 비교(`canViewLogsOf`)에는 등호가 없어 자기 로그를 아무도 못 본다. 본인 예외만 얹고 역할 비교는 그대로 둔다 — 두 규칙을 한 함수에 섞으면 "manager 가 manager 를 본다" 같은 실수가 끼어든다.

**`lib/membership.ts` 의 `statusAfterUnban` 을 지웠다.** §7.1 은 "차단을 풀면 authority 로 이전 상태를 추측한다"고 적지만, 그건 `membership_status` 가 신청 상태와 차단을 **겸했기 때문**에 생긴 우회책이다(§12-19). `isBanned` 를 분리한 지금은 차단이 신청 상태를 건드리지 않아 복원할 것이 없다 — pending 인 채로 차단당한 사람은 pending 으로 돌아온다. 추측 함수를 남기면 호출해서 멀쩡한 상태를 덮어쓰는 함정이 된다.

**개발용 스위치** (`src/mocks/config.ts`) — 세 상태를 눈으로 확인하기 위한 장치다. 정상 응답만 오면 로딩·빈·에러를 설계할 방법이 없다.

**픽스처의 개인정보 처리** — 구 시드(`C:\code\WEB\...\sql\seeds\`)에는 실명과 입학연도로 시작하는 **실제 학번**이 들어 있다. `Pegasus` 저장소는 GitHub 공개 원격이 붙어 있으므로 옮기지 않았다. 구성(2026 시즌 40명 = 감독 1 · 회장 1 · 선수 32 · 매니저 3 · 영구결번 3)만 참고하고 이름·학번은 가공값이다. 학번 5번째 자리 `9` 가 합성값 표식이다.

`overflow: hidden` 은 스크롤 컨테이너를 만들어 안쪽 sticky 를 망가뜨린다. 두 겹으로 나눠 해결했다.

375px 에서 `scrollLeft = 400` 으로 밀어도 이름 열이 `left: 17px` 에 그대로 있는 것을 브라우저로 확인했다.

> **함께 확인된 제약**: 가로 스크롤 컨테이너 안에서는 **헤더를 페이지 기준으로 sticky 시킬 수 없다.** CSS 사양상 한 축을 `auto` 로 두면 다른 축도 스크롤 컨테이너가 되기 때문이다. 모바일에서 더 중요한 것은 이름 열 고정이라 그쪽을 택했다.

### 관리자 `/admin` ✅ (manager+)

탭 8개. **권한 없는 탭은 렌더하지 않는다** — 존재를 알리고 막는 것보다 낫다는 기존 결정을 따른다.

| 권한 | 탭 |
|---|---|
| manager+ | 멤버 승인 · 로스터 |
| staff+ | + 매니저 · 일반유저 · 멤버 · 차단 계정 · 설정 |
| root | + 스태프 |

- **대상 조건을 서버가 판정한다.** 매니저를 매니저로 임명하거나 멤버를 매니저 해제하는 등 조건이 어긋나면 **409** 로 알린다. 목록이 낡아서 생기는 일이므로 화면을 옮기지 않고 그 자리에 표시한다
- `AdminTable` 이 **≤768px 에서 각 행을 카드로 바꾼다**(§12-26). 표를 가로 스크롤로 감싸면 행마다 있는 액션 버튼을 누르러 스크롤 끝까지 밀어야 한다
- 상태 배지는 **팔레트를 늘리지 않고** 기존 토큰 + 라벨로 구분한다(아래 "미해결 항목 2" 참고)

### 활동내역 `/user/:username` ✅ (member+) · 로그 상세 `/user/:username/log/:logId`

- 게시글 · 댓글 · **활동 로그** 탭. 로그 탭 노출 여부를 **서버가 `canViewLogs` 로 내려준다** — 화면이 스스로 판단하지 않는다
- 로그 상세는 **URL 로 직접 열고 새로고침해도 동작한다**(§12-11)

### 브라우저 검증이 저장소로 들어왔다

지금까지 브라우저 검증 **17개 스위트 약 2,600줄**이 임시 폴더에만 있었다. 저장소에
없으니 `npm test` 에 걸리지 않았고, **다른 PC·새 세션에서는 실행 자체가 불가능**했다
(다른 프로젝트의 `node_modules` 절대 경로를 빌려 쓰고 있었다).

`frontend/e2e/` 로 옮기고 `playwright` 를 devDependency 로 추가했다.

```
npm run e2e            전 스위트 (개발 서버가 없으면 직접 띄운다)
npm run e2e:fast       느린 것(반응형·헤디드) 제외
npm run e2e board      이름으로 걸러 실행
npm run verify         typecheck + lint + test + build + e2e
```

스위트는 **각각 독립 프로세스로 순차 실행**한다. 목의 쓰기 상태가 탭 메모리에 있어
병렬로 돌리면 서로 간섭한다.

> **옮기면서 드러난 것들.** 이관은 단순 복사가 아니었다.
>
> - `home` · `records` · `roster` 세 스위트의 `ok()` 가 **실패를 세지 않고 출력만 했다.** ✗ 가 떠도 항상 성공으로 끝났다 — 낡은 단언이 오래 묻혀 있던 이유다
> - `auth` 스위트가 `/board/12` 처럼 **없는 글 id** 를 하드코딩해, 권한 검사와 리소스 존재 여부가 섞여 있었다. 실제 id 를 받아오도록 고쳤다
> - `auth` 의 기대표가 글 수정을 "member+ 통과"로 적고 있었다. **§12-7 이후 실제 규칙은 소유자만**이다 — 매니저·스태프·root 도 403 이다. 표를 규칙에 맞게 고쳤다
> - `routes` · `ui` · `msw` 세 스위트는 **자리표시자 시절 스모크 테스트**라 지금은 전부 실패한다. 뒤에 만든 상세 스위트가 대체했으므로 옮기지 않았다

### 날짜를 로컬 기준으로 통일했다

`PostForm` 의 `todayPlus` 가 `toISOString().slice(0, 10)` 을 썼다. 이건 **UTC 날짜**라
한국에서 자정~오전 9시 사이에 전날이 나온다 — 오전 8시에 "7일 뒤"를 계산하면
**2026-09-08**(하루 짧음)이 나왔다. 상단 고정이 하루 일찍 풀린다.

같은 포맷 로직이 화면 여섯 곳에 흩어져 있었고 **그중 한 곳만 UTC 를 썼다**
(`EventWrite` 는 처음부터 로컬 기준으로 맞게 하고 있었다). `src/lib/date.ts` 한 곳으로
모으고 17개 테스트로 고정했다 — 시간대에 의존하지 않도록 로컬 필드와 대조하는 방식이다.

**권한 매트릭스 테스트** (`src/lib/roles.test.ts`)

§11.4 가 "재구축 시 최우선 개선 항목"으로 지적한 부분이다. 구 프로젝트에는 자동화 테스트가 전혀 없었다. Vitest 를 추가하고 §4.4 표를 그대로 코드로 옮겼다 — 표 한 줄이 배열 하나(`[비로그인, basic, member, manager, staff, root]`)에 대응한다.

**변이 테스트로 실효성을 확인했다.** `canBanUser` 의 staff 대상 판정을 `isRoot` → `isStaffRole` 로 일부러 바꾸자 해당 테스트만 정확히 실패했고, 되돌리니 통과했다. 테스트가 실제로 회귀를 잡는다.

**검증이 잡아낸 버그 4건** (인증 작업 중)

정적 검사(타입·린트)로는 하나도 걸리지 않았고, 전부 브라우저 검증에서 나왔다.

| 버그 | 증상 | 원인 · 수정 |
|---|---|---|
| **자동 로그인이 무의미** | 새로고침하면 `localStorage` 에 토큰이 있는데도 로그아웃 | 목 세션이 페이지 메모리에만 있어 새로고침 시 소실. 실제 JWT 가 서명으로 자기 완결성을 갖듯, 목 토큰도 사용자 id 를 담아 복원하게 함 |
| **잘못된 `/401` 리다이렉트** | 로그인 상태인데 보호 라우트가 전부 `/401` 로 감 | `finally { setLoading(false) }` 가 **abort 시에도 실행**돼, 사용자 확인 전에 "비로그인" 으로 확정됐다. StrictMode 만의 문제가 아니라 빠른 화면 전환마다 발생. `finally` 를 없애고 성공·실패 경로에서만 내리도록 수정 |
| **320px 헤더 2px 넘침** | 아주 좁은 화면에서 가로 스크롤 | 브랜드 + 개발 메뉴 + 테마 토글 + 햄버거가 안 들어감. ≤360px 에서 간격·여백 축소. **통합 회귀 검사가 발견했다 — 화면마다 따로 쟀으면 또 놓쳤다** |
| **목 비밀번호가 배포물에 누출** | 프로덕션 번들에 `Pegasus!2026` 포함 | `Header` → `devAuth` → 픽스처로 이어지는 **정적 import** 때문. 전환기가 픽스처를 import 하지 않고 목 서버에 계정 목록을 물어보도록 변경 |

**겪은 문제와 원인**

개발 서버에서 `Cannot read properties of null (reading 'useRef')` — React 사본이 둘이라는 오류가 났다. 원인은 **`react-router` 를 import 하기 전에 개발 서버를 띄워서** Vite 의 의존성 사전 번들 캐시가 낡은 것이었다. `node_modules/.vite` 삭제 후 재시작하니 해소됐다. 코드 문제가 아니었다(프로덕션 빌드는 계속 성공했다).
→ **의존성을 추가한 뒤에는 개발 서버를 재시작할 것.**

curl 은 SPA 의 HTML 껍데기만 받으므로 이 오류를 잡지 못했다(모든 경로가 200 을 반환했다). **라우팅 검증은 반드시 실제 브라우저로 해야 한다.**

**412px 가로 스크롤 신고 — 레이아웃 버그가 아니었다**

삼성폰 비율(412×915)에서 좌우 스크롤이 생긴다는 신고를 받고 조사했다. 결론은 **DevTools 기기 모드의 확대**였다. 사용자 콘솔에서 잰 값이 `넘침: 0` · `clientWidth: 412` · **`visualViewport: 334`** 였다 — 페이지는 412px 로 정상 배치돼 있는데 화면이 1.23배 확대돼 334px 만 보이던 것이다. `Ctrl+Shift+M` 으로 기기 모드를 껐다 켜니 해소됐다.

다만 **그때 드러난 검증의 구멍은 실재했다.** 폭 375·320 만 쟀고, 기록 화면은 타자 탭에서만, 모바일은 라이트 테마에서만 확인했었다. 그래서 통합 회귀 검사를 만들었고, 실제로 320px 헤더 넘침을 잡아냈다.

## 목이 증명하는 것과 못 하는 것

백엔드를 만들 때 **"목에서 됐으니 됐다"고 넘기면 안 되는 것**을 구분해 둔다.

**목이 확정하는 것** — 이건 계약이다. 백엔드는 여기에 맞춰 만들면 된다.

- API 계약: 경로 · 요청/응답 모양 · 상태 코드
- 권한 판정: 401/403/409 를 **서버가 실제로 반환한다.** 프론트 가드가 협조해야만 성립하는 설계는 목이 먼저 거절한다
- 화면 흐름과 로딩 · 빈 · 에러 상태
- 투표 표 보존 규칙(§12-8)과 익명 자료구조의 모양(§12-9)

**목이 증명하지 못하는 것** — 백엔드에서 다시 확인해야 한다.

| 항목 | 왜 |
|---|---|
| DB 트랜잭션 · 동시성 | 목은 단일 스레드 JS 다. 동시 투표 경쟁이나 UNIQUE 위반 경쟁을 재현할 수 없다 |
| FK · `ON DELETE CASCADE` | 목은 딸린 댓글·투표를 **손으로** 지운다. 실제 제약 동작과 다르다 |
| 비밀번호 해싱 | 목 계정은 평문 상수를 쓴다. **비밀번호 변경도 평문을 그대로 바꾼다** — 실제 백엔드는 반드시 해싱해야 한다 |
| 탈퇴의 원자성 | 목은 글·댓글·로그를 순서대로 손으로 익명화한다. 실제 DB 는 **한 트랜잭션**이어야 하며, 중간에 실패하면 계정만 사라지고 데이터가 붕 뜬다 |
| rate limit (§12-5) | 목에 없다 |
| 실제 메일 발송 | 인증 코드를 응답에 담아 화면에서 확인한다 |
| 외부 리그 API | 픽스처로 대체했다 |
| **외부 공휴일 API** | 동기화 버튼은 픽스처를 다시 심을 뿐이다. 실제 호출·실패·쿼터 소진은 백엔드에서 확인해야 한다 |

## 남은 범위의 확정 사항 (2026-09-02 검토)

게시판 · 마이페이지 · 관리자 · 활동내역을 만들기 전에 블루프린트를 다시 훑어 정한 것들이다.
구 구현에는 **파이프라인이 실제로 깨진 곳**과 **개발하다 만 기능**이 섞여 있었다.

### 정책 결정 4건

| # | 항목 | 결정 |
|---|---|---|
| A | **게시글 목록 페이지네이션** (§12-14) | **서버로 옮긴다.** `page`/`size` 파라미터로 계약을 바꾼다. 구 구현은 전체 행을 매번 반환하고 클라이언트가 15개씩 잘랐다 — 글이 쌓이면 선형으로 느려진다 |
| B | **게시글 수정 권한** (§12-7) | **수정은 소유자만, 삭제만 manager+.** 구 구현은 서버가 manager+ 수정을 허용하는데 UI 는 소유자에게만 버튼을 보여 서로 어긋났다. 이 결정으로 §12-8(투표 수정) 문제도 함께 사라진다 |
| C | **익명 투표** (§12-9) | **진짜 익명으로 만든다.** `poll_votes` 에 `user_id` 를 남기지 않고, 중복 방지는 별도 참여 테이블로 분리한다. 구 구현은 익명 투표에도 `user_id` 를 저장하고 조회 시점에만 가렸다 — 화면 표시와 실제가 달랐다 |
| D | **회원 탈퇴** (§12-12) | **익명화.** 계정은 지우되 글·댓글은 "탈퇴한 회원"으로 남긴다. 구 구현은 글을 DELETE 해서 **그 글에 달린 타인의 댓글과 투표까지 CASCADE 로 지웠고**, 감사 로그도 함께 소멸시켰다 |

### 결정이 필요 없어 그대로 고칠 것

| 항목 | 조치 |
|---|---|
| **내 로그를 내가 볼 수 없다** (§8.4) | 열람 규칙이 "열람자 > 대상"이라 등호가 없어 **자기 로그를 아무도 못 본다.** 본인 예외를 넣고 마이페이지에 활동 로그를 추가한다 |
| **승인 후 학번을 고칠 방법이 없다** (§7.1) | 프로필 수정은 `none`/`rejected` 일 때만 열리는데, 관리자 API 에도 유저 학번을 고치는 경로가 없다. 관리자용 프로필 수정 엔드포인트를 만든다 |
| **비밀번호를 바꿀 수 없다** (부록 A) | `/api/mypage` 에 엔드포인트 자체가 없고 UI 는 disabled 버튼만 있었다. 마이페이지에 추가한다 |
| **멤버 승인이 조용히 실패** (§12-10) | `UPDATE ... WHERE authority='basic'` 이라 대상이 이미 member+ 면 아무것도 안 바뀌는데 성공 응답에 로그까지 남는다. `affectedRows` 를 확인해 409 로 알린다 |
| **로스터 연동이 문자열 매칭** (§12-17) | `roster.user_id` FK 를 실제로 채운다. 기록 화면의 등번호도 **이름이 아니라 학번 기준**으로 붙인다 — 지금은 동명이인이 충돌한다 |
| **탈퇴·투표 제출이 로그에 안 남는다** (§8.3) | 감사 로그 대상에 추가한다. 특히 탈퇴는 흔적이 남아야 한다 |
| **AccountTab 의 "예시" 섹션** (§12-23) | "비밀번호 변경 (예시)" · "회원 탈퇴 (예시)" 는 이식하지 않는다. 탈퇴는 설정 탭에 이미 있어 중복이자 혼동 요인이었다 |

### 검토했으나 그대로 두는 것

- **비공개 투표 결과를 manager 는 볼 수 없다**(staff/root 만). 매니저가 그 글을 삭제할 수는 있어 권한이 살짝 어긋나 보이지만, 결과 열람과 게시물 관리는 다른 성격이라 블루프린트 규칙을 유지한다
- **조회수가 fire-and-forget**(§12-21). 새로고침마다 오르고 실패해도 알 수 없다. 정확도가 중요한 값이 아니라 우선순위를 낮춘다
- **카카오 로그인 · SMS 인증**(부록 A). 컬럼과 disabled 버튼만 있던 미착수 기능이다. 타입에서 이미 제외했고 새로 만들지 않는다
