# 에러 화면 명세

구 사이트는 `/unauthorized` 하나가 "비로그인"과 "권한 부족"을 내부 분기로 처리했다.
새 사이트는 **에러 화면을 전부 숫자 라우트로 나눈다** — URL만 봐도 왜 막혔는지 알 수 있어야 한다.

> **상태 (2026-09-02) — 프론트엔드 화면 11/11 완료**
> - 에러 화면 4종과 라우트, `returnTo` 처리, `ErrorBoundary` → `/500`, `*` → `/404`: **구현 완료**
> - **2절의 권한 기반 이동: 구현 완료.** `ProtectedRoute` 가 §6.1 표대로 막는다.
>   6개 계정 × 보호 라우트 9개 = **54개 조합을 브라우저로 검증**했다
> - 3절 인라인 처리: 로그인 · 회원가입 · 일정 중복(409) · **게시글/댓글 검증(400) · 익명 재투표(409)** 구현 완료
> - **`/404`·`/403` 도달 경로 전부 구현 완료** — 없는 글 · 없는 유저 · 없는 로그 · 로그 열람 권한 부족까지 브라우저로 확인

---

## 1. 에러 화면 목록

| 라우트 | 의미 | 화면 구성 |
|---|---|---|
| `/401` | 인증 필요 · 세션 만료 | 로그인 버튼 (`returnTo` 로 원래 경로 복귀) |
| `/403` | 로그인은 했으나 권한 부족 | 현재 권한 표시 + 홈으로 |
| `/404` | 없는 경로 · 없는 리소스 | 홈으로 |
| `/500` | 서버 오류 · 렌더 예외 | 재시도 + 홈으로. `ErrorBoundary` 가 렌더한다 |

네 화면은 `ErrorPage` 공통 레이아웃(숫자 · 제목 · 설명 · 액션)을 공유한다.

---

## 2. 도달 경로 맵 — 화면이 이동하는 경우

라우트 가드가 막거나 리소스가 없을 때다.

| 출발 화면 | 조건 | 이동 |
|---|---|---|
| `/board` | 비로그인 | `/401` |
| `/board/:id` | 비로그인 | `/401` |
| `/board/:id` | `basic` (member 미만) | `/403` ✅ 확인 — 라우트 가드와 **API 403** 양쪽 |
| `/board/:id` | 없는 글 id | `/404` ✅ 확인 |
| `/board/write` | 비로그인 | `/401` |
| `/board/write` | member 미만 | `/403` |
| `/board/:id/edit` | 비로그인 | `/401` |
| `/board/:id/edit` | 글 소유자가 아님 | `/403` ✅ 확인 — 매니저도 타인 글은 못 고친다(§12-7) |
| `/board/:id/edit` | 없는 글 id | `/404` ✅ 확인 |
| `/schedule/write` | 비로그인 | `/401` |
| `/schedule/write` | manager 미만 | `/403` |
| `/mypage` | 비로그인 | `/401` |
| `/admin` | 비로그인 | `/401` |
| `/admin` | manager 미만 | `/403` |
| `/user/:username` | 비로그인 | `/401` ✅ 확인 |
| `/user/:username` | member 미만 | `/403` ✅ 확인 — API 도 403 |
| `/user/:username` | 없는 유저 | `/404` ✅ 확인 |
| `/user/:username` 로그 탭 | 열람자 권한이 대상보다 높지 않음 | **탭 자체를 렌더하지 않는다.** 서버도 API 를 403 으로 막는다(§12-2) ✅ 확인 |
| `/user/:username/log/:logId` | 로그 열람 권한 없음 | `/403` ✅ 확인 |
| `/user/:username/log/:logId` | 없는 로그 id · 그 사용자의 로그가 아님 | `/404` ✅ 확인 |
| `/admin` | manager 미만 | `/403` ✅ 확인 |
| `/mypage` | 승인 후 프로필 수정 시도 | **이동하지 않는다.** 화면이 애초에 수정 UI 를 내지 않고, API 직접 호출만 403 (§7.1) ✅ 확인 |
| `/mypage` | root 계정의 탈퇴 시도 | **이동하지 않는다.** 버튼 자체가 없고 API 직접 호출만 403 (§7.4) ✅ 확인 |
| 매칭되지 않는 임의 경로 | — | `/404` |
| **모든 화면** | 토큰 만료 → API 401 | `/401` |
| **모든 화면** | 렌더 중 예외 (`ErrorBoundary`) | `/500` |

> **다만 화면의 주제 자체가 없으면 `/404` 로 보낸다.** 게시글 상세는 글 하나가 페이지의 전부라, 그 자리에 오류 박스를 그려 봐야 보여줄 것이 없다. 위젯 하나가 실패한 것과는 다른 경우다.

> **데이터 조회 실패는 화면을 옮기지 않는다.** 처음에는 "API 5xx → `/500`" 으로 적었으나 구현하면서 바꿨다. 위젯 하나가 실패했다고 페이지 전체를 500 으로 갈아치우면 멀쩡한 나머지까지 못 보게 된다. `useApiResource` 는 오류를 돌려주기만 하고, 화면이 그 자리에 `ErrorState`(다시 시도 버튼 포함)를 그린다. `/500` 은 **렌더 자체가 터진 복구 불가 상황** 전용이다.

공개 화면(`/`, `/roster`, `/schedule`, `/records`, `/login`, `/signup`)은 권한 때문에 에러 화면으로 이동하지 않는다. 리소스 부재(`/404`)와 서버 오류(`/500`)만 해당된다.

## 3. 화면이 이동하면 안 되는 경우 — 인라인 표시

**페이지를 갈아치우면 사용자가 입력하던 내용을 잃는다.** 아래는 반드시 제자리에서 표시한다.

| 위치 | 조건 | 표시 방식 |
|---|---|---|
| `/login` | 아이디·비밀번호 불일치 (401) | 폼 하단 메시지. **아이디 존재 여부를 구분하지 않는다** (계정 열거 방지) |
| `/login` | 차단된 계정 (403) | 폼 하단 메시지 |
| `/signup` | username·email 중복 (409) | 해당 필드 인라인 |
| `/signup` | 이메일 인증 코드 불일치 (400) | 코드 입력란 인라인 |
| `/schedule/write` | 일정 중복 `UNIQUE(date,name)` (409) | 실패한 건만 하단에 목록으로 수집 ✅ **구현 완료** — 입력한 행이 그대로 남는 것을 브라우저로 확인 |
| `/board/write`, `/board/:id/edit` | 검증 실패 (400) | 폼 하단 메시지 ✅ **구현 완료** — 입력한 내용이 그대로 남는다 |
| `/board/:id` | 익명 투표 재시도 (409) | 투표 블록 안에 메시지 ✅ **구현 완료** |
| `/board/:id` | 댓글 500자 초과 (400) | 입력란 아래 메시지 + 실시간 카운터 ✅ **구현 완료** |
| `/board/:id` | 삭제 실패 | 확인 모달을 닫고 본문 하단에 메시지. 모달을 열어둔 채 두지 않는다 |
| `/mypage` 계정 | 아이디·이메일 중복 (409) | 폼 하단 메시지 ✅ **구현 완료** |
| `/mypage` 계정 | 이메일 인증 미완료 (400) | 폼 하단 메시지 ✅ **구현 완료** — 화면에서도 막지만 서버가 다시 검사한다(§12-3) |
| `/mypage` 계정 | 비밀번호 변경 실패 (400) | 폼 하단 메시지 ✅ **구현 완료** — 현재 비밀번호 불일치·규칙 위반·같은 값 |
| `/mypage` 계정 | 멤버 신청 전제조건 (400) | 사유별로 다른 메시지 ✅ **구현 완료** (§7.1) |
| `/mypage` 설정 | 탈퇴 실패 | 확인 모달을 닫고 섹션 하단에 메시지 |
| 모든 폼 | 검증 실패 (400) | 필드별 인라인 |
| `/admin` 각 탭 | 권한 없는 탭 | **탭 자체를 렌더하지 않는다** ✅ 확인 — manager 2탭 / staff 7탭 / root 8탭 |
| `/admin` 멤버 승인 | 대상이 이미 멤버 (409) | 목록 위에 메시지 ✅ **구현 완료** — 목록이 낡아서 생기는 일이라 "새로 고쳐 달라"고 알린다(§12-10) |
| `/admin` 권한 변경 | 대상 조건 불일치 (409) | 같은 방식 ✅ **구현 완료** |
| `/admin` 로스터 | 같은 해 학번 중복 (409) · 검증 실패 (400) | 추가 폼 아래 인라인 ✅ **구현 완료** — 입력한 값이 그대로 남는다 |
| `/admin` 차단 | 대상 역할에 대한 권한 부족 (403) | **여기서는 화면을 옮기지 않는다.** 목록이 낡았을 뿐이므로 그 자리에 알린다 |

---

## 4. 왜 어떤 것은 숨기고 어떤 것은 403 인가

**`/admin` 내부 탭은 숨긴다.** 스태프 관리는 `root`, 일반유저·멤버·차단 계정·연도 설정은 `staff+` 전용이다. 이들은 탭 자체를 렌더하지 않는다 — 존재를 알리고 막는 것보다 낫고, 구 구현도 같은 방식이었다.

**라우트 단위 접근은 `/403` 으로 보낸다.** URL 을 직접 입력한 사용자에게 아무 반응이 없으면 고장으로 오인한다.

**목록 안의 행 액션이 403·409 를 받으면 화면을 옮기지 않는다.** 대개 목록이 낡아서 생기는 일이라, 사용자에게 필요한 것은 에러 화면이 아니라 "새로 고쳐 보라"는 안내다. 라우트 진입 자체가 막히는 것과는 다른 경우다.

## 5. 구현 시 지켜야 할 것

**status → 화면 이동 매핑은 `src/lib/api.ts` 한 곳에 둔다.** 각 호출부가 제각기 판단하면 위 표가 금방 어긋난다. 3절의 인라인 케이스를 위해 **호출부에서 자동 이동을 끌 수 있는 옵션**을 제공한다.

**프론트엔드 가드는 UX 장치일 뿐이다.** 블루프린트 §12-1, §12-2 는 구 사이트가 프론트엔드 가드만 믿고 게시판 본문·활동 로그 API 를 공개해 둔 결함을 지적한다. 위 표대로 화면을 막더라도, **실제 차단은 항상 서버가 해야 한다.** MSW 핸들러도 이 원칙대로 401/403 을 실제로 반환한다.

게시판에서 이것을 실제로 확인했다 — 토큰 없이 `GET /api/posts/:id` 와 `GET /api/comments` 를 부르면 **401** 이고, basic 계정으로 부르면 **403** 이다. 구 구현은 같은 호출에서 본문이 그대로 나왔다.

**탈퇴 직후에는 `/401` 로 보내지 않는다.** 방금 스스로 계정을 지운 사람에게 "로그인이 필요합니다"는 맞지 않는다. 홈으로 보낸다.

구현할 때 함정이 하나 있었다. react-router 의 `navigate` 는 transition(낮은 우선순위)이고 `logout()` 의 `setUser(null)` 은 긴급 업데이트라, 나란히 호출하면 **긴급 쪽이 앞질러 아직 `/mypage` 인 상태로 user 가 null 인 렌더**가 생기고 `ProtectedRoute` 가 `/401` 로 보낸다. 호출 순서를 바꾸거나 `setTimeout` 으로 미뤄도 소용없고, **둘을 하나의 `startTransition` 으로 묶어야** 한다.

**"눌리는데 안 열리는" 화면을 만들지 않는다.** 구 게시판은 basic 사용자에게 제목을 링크로 보여주고 클릭만 `preventDefault` 로 막았다. 반응이 없는 링크는 고장으로 보인다. 열 수 없으면 **링크를 만들지 않고 그 이유를 적는다.**

## 6. 검증 방법

Phase 3 의 개발 전용 역할 전환기로 `basic → member → manager → staff → root` 를 순회하며 **2절 표를 한 행씩 재현한다.**

3절 표는 **화면이 바뀌지 않는지**를 확인한다. 특히 `/schedule/write` 에서 중복 일정을 넣었을 때 입력하던 다른 행들이 그대로 남아 있어야 한다.
