# 에러 화면 명세

구 사이트는 `/unauthorized` 하나가 "비로그인"과 "권한 부족"을 내부 분기로 처리했다.
새 사이트는 **에러 화면을 전부 숫자 라우트로 나눈다** — URL만 봐도 왜 막혔는지 알 수 있어야 한다.

> **상태 (2026-09-01)**
> - 에러 화면 4종과 라우트, `returnTo` 처리, `ErrorBoundary` → `/500`, `*` → `/404`: **구현 완료**
> - **2절의 권한 기반 이동: 구현 완료.** `ProtectedRoute` 가 §6.1 표대로 막는다.
>   6개 계정 × 보호 라우트 9개 = **54개 조합을 브라우저로 검증**했다
> - 3절 인라인 처리: 로그인·회원가입 해당분 **구현 완료**. 나머지(일정 중복 409, 게시글 폼)는 해당 화면이 아직 자리표시자다
> - 리소스 부재로 인한 `/404`(없는 글·유저·로그)는 해당 화면 구현 시 붙인다

---

## 1. 에러 화면 목록

| 라우트 | 의미 | 화면 구성 |
|---|---|---|
| `/401` | 인증 필요 · 세션 만료 | 로그인 버튼 (`returnTo` 로 원래 경로 복귀) |
| `/403` | 로그인은 했으나 권한 부족 | 현재 권한 표시 + 홈으로 |
| `/404` | 없는 경로 · 없는 리소스 | 홈으로 |
| `/500` | 서버 오류 · 렌더 예외 | 재시도 + 홈으로. `ErrorBoundary` 가 렌더한다 |

네 화면은 `ErrorPage` 공통 레이아웃(숫자 · 제목 · 설명 · 액션)을 공유한다.

---

## 2. 도달 경로 맵 — 화면이 이동하는 경우

라우트 가드가 막거나 리소스가 없을 때다.

| 출발 화면 | 조건 | 이동 |
|---|---|---|
| `/board` | 비로그인 | `/401` |
| `/board/:id` | 비로그인 | `/401` |
| `/board/:id` | `basic` (member 미만) | `/403` |
| `/board/:id` | 없는 글 id | `/404` |
| `/board/write` | 비로그인 | `/401` |
| `/board/write` | member 미만 | `/403` |
| `/board/:id/edit` | 비로그인 | `/401` |
| `/board/:id/edit` | 글 소유자가 아님 | `/403` |
| `/board/:id/edit` | 없는 글 id | `/404` |
| `/schedule/write` | 비로그인 | `/401` |
| `/schedule/write` | manager 미만 | `/403` |
| `/mypage` | 비로그인 | `/401` |
| `/admin` | 비로그인 | `/401` |
| `/admin` | manager 미만 | `/403` |
| `/user/:username` | 비로그인 | `/401` |
| `/user/:username` | member 미만 | `/403` |
| `/user/:username` | 없는 유저 | `/404` |
| `/user/:username/log/:logId` | manager 미만 | `/403` |
| `/user/:username/log/:logId` | 없는 로그 id | `/404` |
| 매칭되지 않는 임의 경로 | — | `/404` |
| **모든 화면** | 토큰 만료 → API 401 | `/401` |
| **모든 화면** | 렌더 중 예외 (`ErrorBoundary`) | `/500` |

> **데이터 조회 실패는 화면을 옮기지 않는다.** 처음에는 "API 5xx → `/500`" 으로 적었으나 구현하면서 바꿨다. 위젯 하나가 실패했다고 페이지 전체를 500 으로 갈아치우면 멀쩡한 나머지까지 못 보게 된다. `useApiResource` 는 오류를 돌려주기만 하고, 화면이 그 자리에 `ErrorState`(다시 시도 버튼 포함)를 그린다. `/500` 은 **렌더 자체가 터진 복구 불가 상황** 전용이다.

공개 화면(`/`, `/roster`, `/schedule`, `/records`, `/login`, `/signup`)은 권한 때문에 에러 화면으로 이동하지 않는다. 리소스 부재(`/404`)와 서버 오류(`/500`)만 해당된다.

---

## 3. 화면이 이동하면 안 되는 경우 — 인라인 표시

**페이지를 갈아치우면 사용자가 입력하던 내용을 잃는다.** 아래는 반드시 제자리에서 표시한다.

| 위치 | 조건 | 표시 방식 |
|---|---|---|
| `/login` | 아이디·비밀번호 불일치 (401) | 폼 하단 메시지. **아이디 존재 여부를 구분하지 않는다** (계정 열거 방지) |
| `/login` | 차단된 계정 (403) | 폼 하단 메시지 |
| `/signup` | username·email 중복 (409) | 해당 필드 인라인 |
| `/signup` | 이메일 인증 코드 불일치 (400) | 코드 입력란 인라인 |
| `/schedule/write` | 일정 중복 `UNIQUE(date,name)` (409) | 실패한 건만 하단에 목록으로 수집 |
| `/board/write`, `/board/:id/edit` | 검증 실패 (400) | 필드별 인라인 |
| 모든 폼 | 검증 실패 (400) | 필드별 인라인 |
| `/admin` 각 탭 | 권한 없는 탭 | **탭 자체를 렌더하지 않는다** |

---

## 4. 왜 어떤 것은 숨기고 어떤 것은 403 인가

**`/admin` 내부 탭은 숨긴다.** 스태프 관리는 `root`, 일반유저·멤버·차단 계정·연도 설정은 `staff+` 전용이다. 이들은 탭 자체를 렌더하지 않는다 — 존재를 알리고 막는 것보다 낫고, 구 구현도 같은 방식이었다.

**라우트 단위 접근은 `/403` 으로 보낸다.** URL 을 직접 입력한 사용자에게 아무 반응이 없으면 고장으로 오인한다.

---

## 5. 구현 시 지켜야 할 것

**status → 화면 이동 매핑은 `src/lib/api.ts` 한 곳에 둔다.** 각 호출부가 제각기 판단하면 위 표가 금방 어긋난다. 3절의 인라인 케이스를 위해 **호출부에서 자동 이동을 끌 수 있는 옵션**을 제공한다.

**프론트엔드 가드는 UX 장치일 뿐이다.** 블루프린트 §12-1, §12-2 는 구 사이트가 프론트엔드 가드만 믿고 게시판 본문·활동 로그 API 를 공개해 둔 결함을 지적한다. 위 표대로 화면을 막더라도, **실제 차단은 항상 서버가 해야 한다.** MSW 핸들러도 이 원칙대로 401/403 을 실제로 반환하도록 작성한다.

---

## 6. 검증 방법

Phase 3 의 개발 전용 역할 전환기로 `basic → member → manager → staff → root` 를 순회하며 **2절 표를 한 행씩 재현한다.**

3절 표는 **화면이 바뀌지 않는지**를 확인한다. 특히 `/schedule/write` 에서 중복 일정을 넣었을 때 입력하던 다른 행들이 그대로 남아 있어야 한다.
